# CIP-113: Programmable Token-Like Assets

**Status:** Accepted by CIP editors, awaiting merge into official repo (PR #444). Not yet "Active" but spec is stable enough that Cardano Foundation has reference implementations in Aiken.

**Solves:** CPS-0003 (Smart Tokens)

---

## Core Idea

Native Cardano assets with programmable rules enforced on every transfer, mint, and burn. Think "smart tokens" — not a new token type, but native assets wrapped in a shared custody + validation framework.

## How It Works

- All tokens of a given policy live at a single shared script address (the "programmable logic base")
- Ownership is tracked by **stake credential**, not payment credential
- An on-chain registry links each token policy to its validation modules
- Every transfer triggers a chain: `programmable_logic_base` → dispatcher → delegate (transfer/third_party/unfracking) → module's logic script
- Uses **withdraw-zero pattern** for composable, once-per-transaction validation

### Architecture

```
All programmable tokens on Cardano → sit at ONE shared address
                    ↓
    ┌───────────────────────────────┐
    │   programmable_logic_base     │
    │   (the single custody script) │
    └──────────────┬────────────────┘
                   ↓
    ┌───────────────────────────────┐
    │  programmable_logic_global    │
    │   (dispatcher — once per tx)  │
    └──────────────┬────────────────┘
                   ↓
    ┌─────────────┬─────────────┬──────────────┐
    ↓             ↓             ↓              ↓
  transfer    third_party   unfracking    issuance_logic
  delegate    delegate      delegate      delegate
    ↓             ↓             ↓              ↓
 [module]     [module]      [module]      [module]
 YOUR RULES   YOUR RULES    YOUR RULES    YOUR RULES
```

### Modules (Substandards)

Modules are pluggable:
- **Simple permissioned transfer**
- **Freeze-and-seize** (denylist, KYC)
- **Custom issuer controls**

## The 12 Validators

| # | Validator | Purpose |
|---|-----------|---------|
| 1 | `programmable_logic_base` | Runs on every spend of a programmable token. Reads dispatcher credential, requires its withdraw-0. |
| 2 | `programmable_logic_global` | The dispatcher. Reads redeemer, requires corresponding delegate's withdraw-0. |
| 3 | `transfer` | Ordinary transfers. Checks ownership proof, registry proof, output shape, delegates to module's transfer logic. |
| 4 | `third_party` | Forced actions (seizure, freeze, burn). Checks registry proof, delegates to module's third-party logic. |
| 5 | `unfracking` | Holder-driven restructuring. Move own tokens around without transferring ownership. |
| 6 | `registry` | Sorted linked list of all registered token policies. Mint = insert/update. Spend = guard node. |
| 7 | `issuance_mint` | Permanent per-token minting policy. Hash = policy ID. |
| 8 | `issuance_logic` | Protocol-side issuance rules (can be upgraded). |
| 9 | `issuance_cbor_hex_mint` | One-shot mint of the issuance script template NFT. |
| 10 | `protocol_params` | One-shot mint of the protocol params NFT + upgrade path. |
| 11 | `upgrade_multisig` | Optional: multisig-gated upgrade authority. |
| 12 | `always_fail` | Locks reference NFTs permanently. |

## Feature Summary

| Feature | How CIP-113 Does It |
|--------------------------|-----------------------------------------------------|
| Where tokens live | One shared script address for ALL programmable tokens |
| Who owns them | Stake credential (your wallet's staking key) |
| Transfer rules | Your module's transfer validator decides |
| Freeze/seize | Your module's third_party validator decides |
| Can I restructure my UTxO? | Yes — unfracking delegate, same-owner only |
| Registry | On-chain sorted linked list of all token policies |
| Who controls the framework | Protocol params NFT with upgrade authority |

## Implications for PACT / PactVote

### Current State
PACT is a simple native asset. PactVote checks wallet holds ≥1 token from policy X. That's it.

### With CIP-113, PACT Could:
- **Revocable membership** — issuer can freeze or seize tokens if someone is banned from the pack
- **Programmable transfer rules** — restrict who can receive PACT (e.g., only verified DReps)
- **Expiry/renewal logic** — tokens could have time-based validity baked in
- **On-chain enforcement** — rules enforced at ledger level, not just checked by dApp

### Case For:
- Freeze/seize genuinely useful for pack governance — "minimum punishment: banishment from pack" becomes enforceable on-chain, not just a UI flag
- Real differentiator — few governance dApps use programmable tokens
- Reference implementation exists and is in Aiken (our stack)

### Case Against:
- **Wallet integration is the killer.** Programmable tokens live at a shared script address with stake-credential ownership. Standard wallets don't resolve balances correctly without explicit integration. Users' wallets (Lace, Eternl, etc.) may show zero PACT balance or fail to build transactions.
- **Overkill for the use case.** PACT is a membership token, not a regulated security. Simple minting policy + off-chain checks might be 90% of the value at 10% of the complexity.
- **The standard isn't final.** PR #444 is accepted but not merged. Spec could still shift.

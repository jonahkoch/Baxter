assistant: Great follow-up. The fee was inflatable because of a **broken fee check with a one-sided bound.**

Here's the exact code from the validator:

```
valid_quote_protocol_fees = quote_protocol_fees_delta * f_rev >= -quote_total_delta * protocol_fee_num
```

With the pool's actual parameter `protocol_fee_num = 0`, this becomes:

```
quote_protocol_fees_delta * 99,900 >= 0
```

**Any non-negative number passes.** The attacker could declare 9,869,999,999 lovelace as "protocol fees" and the validator says "sure, that's valid."

**There was no upper bound.** The check only verifies fees don't go *down* too much. It never asks:
- "Are fees less than the total deposit?"
- "Are fees less than the real balance?"
- "Is this fee delta economically reasonable?"

**So any user could have inflated the fee.** It wasn't a privileged operation. The attacker just happened to be the one who realized the check was vacuous.

**Why ~9,870 ADA specifically?**

The attacker needed `protocol_fees_x` to exceed the pool's remaining real ADA balance after the drain. They calculated the exact amount:

- Pool had ~2,424,788 ADA in real balance
- They needed `protocol_fees > real_balance` after Step B
- So they set fees to ~9,870 ADA — more than enough to guarantee the negative reserve

It could have been 100 ADA or 1M ADA. Any amount that made `protocol_fees > real_balance` after the drain would work. The attacker chose ~9,870 because it was just enough to create the negative reserve while minimizing their upfront capital.

**The root cause:** The fee check was designed with `protocol_fee_num > 0` in mind. When the pool was deployed with `protocol_fee_num = 0` (no protocol fees), the right-hand side collapsed to zero, making the check meaningless. A proper implementation would have had a two-sided bound:

```
0 <= quote_protocol_fees_delta <= -quote_total_delta * some_max_rate
```

Or simply: `protocol_fees_delta` must be less than the actual deposit amount. Either fix stops the exploit.

assistant: `f_rev` is a fee-splitting constant. From the incident report:

```
f_rev = 100,000 - lp_fee_num = 99,900
```

So `lp_fee_num` was **100** (0.1% LP fee), making `f_rev = 99,900`.

**What it represents:** It's the portion of trading fees that **doesn't** go to LPs — in this case, 99.9% of the fee logic is tied to `f_rev`, while 0.1% goes to LPs.

**Why it's in the fee check:** The formula:

```
quote_protocol_fees_delta * f_rev >= -quote_total_delta * protocol_fee_num
```

Is checking whether the protocol fees being accrued are "reasonable" relative to the trade size. With `protocol_fee_num = 0`, the right side is 0, so any non-negative `quote_protocol_fees_delta` passes.

**In plain terms:** `f_rev` is just a scaling factor. The bug isn't in `f_rev` itself — it's that when `protocol_fee_num = 0`, the entire inequality collapses to `something * 99,900 >= 0`, which is always true for positive numbers. The `f_rev` value of 99,900 is normal; the missing upper bound is the bug.

## What CIP-0099 Actually Is

**CIP-0099: Proof of Onboarding** (merged, active standard)

- A QR-code-based token claim system for IRL events
- Wallet scans QR → POST request to project server → tokens distributed
- Campaign `code` field enables basic attribution (e.g., "consensus2023")
- Supported by Vespr, Yoroi, Lace, Begin, Eternl Mobile wallets
- HOSKY's `poo-genericClaim` is an open-source server implementation

**What it solves:** Frictionless token distribution at conferences, meetups, events — replacing paper wallets.

**What it does NOT solve:**
- ❌ Campaign configuration for DeFi protocols (not IRL events)
- ❌ Attribution of rewards to on-chain economic activity (deposits, swaps, lending)
- ❌ Auditable reconciliation of spend vs qualifying TVL
- ❌ Broad programmatic distribution beyond QR-code scans

---

## How I Adjusted the Proposals

Changed "currently impossible" → **"currently impossible at scale"** and added:

> *"CIP-0099 and the HOSKY generic claim tool provide a partial solution for IRL event-based token distribution via QR codes... However, it does not address: (a) campaign configuration for DeFi protocols, (b) attribution of rewards to on-chain economic activity, (c) auditable on-chain reconciliation of spend vs qualifying TVL, or (d) broad programmatic distribution beyond IRL events. The full Merkl/Turtle Club-class infrastructure remains absent."*

**Why this is stronger:**
- Shows you've done your homework — you know CIP-0099 exists
- Demonstrates nuance — you can distinguish between a narrow tool and full infrastructure
- Maintains the core argument — the audit's 28.8/100 score still stands
- Prevents an Alpha Growth reviewer from saying "actually, CIP-0099 exists" and dismissing your proposal

The gap is real. CIP-0099 is a proof-of-concept for one narrow use case. What you're proposing is the full infrastructure layer. That's a much bigger and more defensible ask.
